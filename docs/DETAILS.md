# Подробная документация

[← Краткая инструкция](../README.md)

Установщик чистого Ubuntu VPS для VPN на базе [3x-ui](https://github.com/MHSanaei/3x-ui): Vision и XHTTP — оба с **REALITY Self-steal**.

## Главное

- [VLESS + TCP/REALITY + XTLS Vision](https://github.com/XTLS/Xray-core) по умолчанию либо выбираемый VLESS + XHTTP/REALITY; оба используют Self-steal на TCP/443.
- [NGINX](https://github.com/nginx/nginx) с сайтом-заглушкой на том же домене, HTTP/2 по ALPN и локальным TLS fallback — для схемы Self-steal.
- TLS-сертификат [Let's Encrypt](https://letsencrypt.org/) обновляется через постоянный webroot Nginx; TCP/80 сохраняет ACME challenge и перенаправляет остальные запросы на HTTPS. Также настраиваются UFW, [BBR](https://www.kernel.org/doc/html/latest/networking/bbr.html), отключение IPv6 и ежедневные обновления безопасности.
- Мастер безопасности с рекомендуемыми значениями по умолчанию: отдельный sudo-пользователь и key-only SSH без прямого входа root либо явно выбираемые режимы root по ключу/сохранения текущей политики; Fail2ban jail для `sshd`.
- Еженедельное обслуживание Ubuntu в воскресенье в 05:00 выбранного часового пояса; reboot выполняется только при наличии `/var/run/reboot-required`.
- Подписки для [HAPP](https://github.com/Happ-proxy/happ-desktop), [INCY](https://incy.cc/) и [Mihomo](https://github.com/MetaCubeX/mihomo) с правилами маршрутизации [RoscomVPN](https://github.com/hydraponique/roscomvpn-routing).
- [Cloudflare WARP](https://www.cloudflare.com/warp/) — дополнительный выход для российских ресурсов (домены и IP): сайт видит адрес WARP вместо адреса VPS. Остальной трафик использует обычный выход. Включён по умолчанию, отключается ответом `no`.
- Самостоятельный VPN-сервер или удалённая нода для существующей панели.
- Панель standalone по умолчанию слушает только `127.0.0.1`; доступны явные режимы SSH/Tailscale, UFW allowlist одного IPv4 и публичный режим.
- Версии установщика 3x-ui, acme.sh и файлы RoscomVPN зафиксированы по commit/tag, а скачанное содержимое проверяется по SHA-256; изменяемый `curl | sh` для ACME не используется.

## Требования

Обязательно:

- Чистый Ubuntu 22.04+ с systemd на `x86_64`/`amd64`, `aarch64`/`arm64`, `armv7l` или `s390x`.
- Первоначальный root-доступ, публичный IPv4 и исходящий доступ в Интернет для APT, GitHub и Let's Encrypt.
- Домен у любого DNS-провайдера с единственной прямой A-записью на IPv4 VPS. AAAA и DNS-прокси использовать нельзя.
- Свободные TCP/80 и TCP/443. Во внешнем firewall провайдера должны быть открыты текущий SSH-порт, TCP/80 и TCP/443.
- Доступные Ubuntu-репозитории `main`, `universe` и `security`.
- Отсутствие установленных 3x-ui, Nginx, `/root/.acme.sh`, старого state этого проекта и настроенных правил UFW.

Опционально:

- SSH-ключ — только для двух key-only режимов. Без ключа можно явно сохранить текущую SSH-политику.
- Доверенный публичный IPv4 — только для режима allowlist панели.
- Главная 3x-ui панель — только для режима удалённой ноды.
- WARP и Tailscale не обязательны.

Установщик сам ставит системные пакеты. Существующий ключ можно перенести из `/root/.ssh/authorized_keys` или вставить вручную.

## Установка

Войдите на VPS как `root` и выполните:

```bash
set -euo pipefail
cd /root
readonly REV='v0.5.0'
for file in install-xhttp-vps.sh finish-xhttp-vps.sh optimize-xhttp-memory.sh xhttp-vps-common.sh; do
  curl -fsSLo "$file" "https://raw.githubusercontent.com/yazmann/xhttp-vps-setup/${REV}/${file}"
done
printf '%s\n' \
  'a57bae37db62f4cd8f61008ce1219caf37de6f91d1561a34476a97ff812313dd  install-xhttp-vps.sh' \
  '71cadfd1c5b487b33996958b8f1dfda525b16dcf491e3ffc72cd7b715d27564f  finish-xhttp-vps.sh' \
  '6001886a100e88218d7de950d8078f7d6c72af5e49d102d53ab4b588dbbbeff1  optimize-xhttp-memory.sh' \
  '5287fc164472f3310c30361bbd3e573d6c7efcd8cfb60e994d4c790026edc9c4  xhttp-vps-common.sh' \
  | sha256sum -c -
chmod 700 install-xhttp-vps.sh finish-xhttp-vps.sh optimize-xhttp-memory.sh xhttp-vps-common.sh
./install-xhttp-vps.sh
```

Команда скачивает одну проверенную ревизию и сверяет SHA-256 каждого root-скрипта до запуска. После первого выпуска стабильные версии также будут доступны через тег и GitHub Release.

Скрипт показывает последствия каждого варианта прямо перед выбором. По умолчанию используются Vision, локальная панель и новый sudo-администратор с key-only SSH; прямой вход root и все SSH-пароли отключаются. После успешной установки выводится готовый блок с панелью и подписками либо с параметрами ноды. Те же данные сохраняются в защищённом файле `/root/xhttp-vps-result-*.txt`.

### Выбор безопасности при установке

| Настройка | Варианты | Значение по умолчанию и рекомендация |
|---|---|---|
| Доступ к панели standalone | Только `127.0.0.1`; один доверенный публичный IPv4; весь Интернет | `127.0.0.1`: открывать с компьютера или телефона через SSH-туннель либо приватный Tailscale Serve. |
| Доступ к панели ноды | Только `127.0.0.1`; один доверенный публичный IPv4; весь Интернет | Один доверенный IPv4 главной панели. Если панель и нода объединены приватной сетью, можно выбрать localhost и организовать приватный маршрут отдельно. |
| SSH | Новый sudo-пользователь по ключу; `root` только по ключу; оставить текущую политику | Новый пользователь по ключу. Вариант `root` сохраняет совместимость, но компрометация ключа сразу даёт полный доступ. Текущая политика не меняется только по явному выбору и может оставить парольный вход. |

Публичная панель — режим повышенного риска: мастер предупреждает о необходимости немедленно включить 2FA, сохранить recovery codes отдельно и ограничить порт во внешнем firewall провайдера. В private-режиме 2FA всё равно полезна как дополнительный слой, но панель не доступна напрямую из Интернета.

Если выбран один из key-only режимов, не закрывайте исходную root-сессию, пока во втором терминале не проверите выбранный вход (и `sudo` для нового администратора):

```bash
ssh -p SSH_PORT SELECTED_USER@vpn.example.com
sudo -n true
```

Пароль нового Linux-пользователя заблокирован; `sudo` разрешён без пароля, потому что сервер принимает только заранее установленный SSH-ключ. Это означает, что защита приватного ключа критична: используйте локальную passphrase и блокировку устройства. Если выбран режим сохранения текущей SSH-политики, установщик явно помечает hardening как `SKIP` и не заявляет, что парольный/root-доступ безопасен.

## Управление

Чтобы снова открыть меню установщика:

```bash
sudo /root/install-xhttp-vps.sh
```

- Пункт `5` — показать текущие настройки; появляется после завершённой установки.
- Если установка прервалась: `sudo /root/finish-xhttp-vps.sh`. При незавершённом bootstrap он продолжает установщик с прежними параметрами, затем возвращается к настройке панели. Повторный ввод домена/паролей не требуется.
- Сохраняйте все четыре `.sh` рядом и обновляйте их вместе. Возобновление bootstrap требует журнала владения новой версии; старые установки без журнала не принимаются автоматически за управляемые этой версией.

## Доступ к панели с компьютера и телефона

Для standalone рекомендуется режим `Private localhost`. Панель не исчезает и не требует физического доступа к VPS: она доступна через уже работающий SSH или приватную overlay-сеть.

Разовый доступ через SSH-туннель:

```bash
ssh -p SSH_PORT -L PANEL_PORT:127.0.0.1:PANEL_PORT SELECTED_USER@vpn.example.com
```

Замените `PANEL_PORT` числом из результата установки и, пока SSH-сессия открыта, перейдите по сохранённому локальному URL панели. В Termius на телефоне создайте Local Port Forwarding с destination host `127.0.0.1`, destination port и local port равными порту панели. Поскольку сертификат панели выпущен на домен, браузер при обращении к `127.0.0.1` может показать несовпадение имени; для постоянного мобильного доступа лучше Tailscale Serve.

После установки Tailscale на VPS и телефон и подключения их к одному tailnet выполните на VPS:

```bash
tailscale serve --bg https+insecure://127.0.0.1:PANEL_PORT
tailscale serve status
```

Открывайте выданный адрес `https://имя-узла....ts.net/PANEL_PATH/` через приложение Tailscale. Используется приватный **Serve**, не публичный Funnel. Установщик намеренно не ставит Tailscale и не получает доступ к вашему tailnet. Правила ACL tailnet должны разрешать доступ только вашим администраторским устройствам.

Режим `Allow one trusted public IPv4` подходит для связи удалённой ноды с главной панелью. Для телефона с меняющимся мобильным IP он неудобен. Публичный режим оставлен только как явная совместимость: сразу включите 2FA в 3x-ui, храните recovery codes отдельно и ограничьте порт firewall провайдера, если это возможно.

## Удаление с архивированием

Перед удалением сохраните нужные данные. Для изменения расхода памяти переустановка не требуется — используйте процедуру ниже.

1. Запустите `sudo /root/install-xhttp-vps.sh`.
2. Выберите пункт `3` и подтвердите удаление ответом `yes` или `y`.

Перед установкой сохраняются исходные управляемые файлы и каталог с журналом `/root/xhttp-managed.*`. При удалении текущие файлы 3x-ui, сайта, сертификата и конфигураций перемещаются в архив `removed.*` внутри этого каталога, а исходные файлы возвращаются. В том числе сохраняются добавленные позже файлы внутри управляемых каталогов. Архив содержит секреты и доступен только root.

Пакеты, swap, созданный Linux-администратор, выбранная SSH policy, SSH-правило UFW, общий ACME-клиент и посторонние конфигурации Nginx остаются: автоматическое возвращение root/password login при удалении VPN было бы небезопасным. Удаляются только firewall-правила с меткой данной установки. `purge` и `autoremove` не запускаются. Пункт `4` выполняет такое же архивирование, сохраняя файл установщика; новую установку автоматически не запускает. Для повторной чистой установки используйте свежий VPS.

У старых установок без журнала автоматическое удаление блокируется: state-файл не доказывает происхождение всех файлов. Не создавайте журнал задним числом из текущего состояния.

## Маршрутизация и проверка трафика

WARP скрывает реальный выходной IP VPS от российских сайтов и приложений. Через него направляются `.ru`, `.su`, `.рф` (`domain:xn--p1ai`), `geosite:category-ru` (включая сервисы в других доменных зонах) и `geoip:ru` (в том числе обращения по IP). Нужны актуальные `geosite.dat` с категорией `category-ru` и `geoip.dat` с категорией `ru`; отсутствие категорий — ошибка, а не повод убрать защиту.

Порядок: служебный API и существующие выходы `blackhole` → российские домены → российские IP → остальные пользовательские маршруты. Таким образом, обычное правило `direct` не обходит WARP для российских ресурсов; относительный порядок внутри каждой группы сохраняется. Неоднозначный catch-all в середине списка или завершающий запрет вызывает ошибку до сохранения. `routing.domainStrategy=IPOnDemand` позволяет проверять IP домена до прямого выхода; `IPIfNonMatch` с прямым catch-all этого не гарантирует.

Домен определяется из запроса клиента или sniffing, IP — непосредственно либо через DNS. При недоступности WARP совпавшие запросы завершаются ошибкой: fallback на `direct` не добавляется. Остальной трафик сохраняет обычные маршруты; это не глобальный VPN для VPS. Списки не гарантируют распознавание всех российских владельцев: неизвестный домен на зарубежном IP может не совпасть. Полноту покрытия нужно проверять и дополнять для нужных сервисов; WARP не означает полной анонимности.

Финальная проверка standalone запускает временный локальный клиент Xray и получает HTTPS-ответ через выбранный VLESS/Vision/REALITY или VLESS/XHTTP/REALITY inbound. Дополнительно проверяются правильный SNI, чужой SNI, ClientHello без SNI, согласование `h2` через ALPN, HTTP→HTTPS redirect и отсутствие страницы панели на fallback. Отдельная проверка WARP требует `warp=on` или `warp=plus` в Cloudflare trace. Этот диагностический запрос к Cloudflare проходит через WARP только во временном процессе; рабочие правила остаются выборочными для российских ресурсов. Временный процесс и файлы удаляются при завершении. Ошибка любого обязательного теста не позволяет объявить установку успешной.

## Транспорт: Vision или XHTTP

`Vision` — основной профиль: `network=tcp`, `flow=xtls-rprx-vision`, REALITY и локальный self-steal. Он рассчитан на максимальную пропускную способность и меньшее количество транспортных состояний.

`XHTTP` — выбираемая альтернатива с тем же локальным REALITY self-steal: `network=xhttp`, пустой `flow`, `mode=auto` и XMUX-профиль. Не добавляйте Vision flow к XHTTP: это другая схема транспорта. Одновременно создать оба профиля на одном IP:443 нельзя; выбор фиксируется в state-файле и recovery сохраняет его.

## Обновления и перезагрузка

`unattended-upgrades` ежедневно устанавливает security-обновления Ubuntu без случайного автоматического reboot. Дополнительно timer `xhttp-vps-maintenance.timer` каждое воскресенье в 05:00 выбранного IANA-часового пояса выполняет `apt update` и обычный `apt upgrade`, проверяет dpkg, Nginx и ключевые службы, после чего перезагружает VPS только при наличии `/var/run/reboot-required`.

Проверка расписания и журнала:

```bash
systemctl list-timers xhttp-vps-maintenance.timer
journalctl -u xhttp-vps-maintenance.service --since '30 days ago'
```

Еженедельный безусловный reboot не используется: он создаёт простой, но ничего не исправляет, если ядро и библиотеки не требуют перезапуска. Timer не имеет `Persistent=true`, поэтому пропущенное ночное окно не вызовет неожиданную дневную перезагрузку. Автоматически обновляются пакеты Ubuntu; 3x-ui, Xray и закреплённые внешние ресурсы обновляются только новой протестированной версией проекта.

У пустой ноды тест VLESS явно помечается `SKIP`: требуется клиент из главной панели. WARP при включении проверяется и на пустой ноде. Локальный тест не проверяет внешний firewall и доступность VPS из сети клиента. Проверка Fail2ban требует активный daemon и загруженный jail `sshd`; отдельный jail панели не нужен, когда панель доступна только через localhost/SSH.

## Маскировка и границы модели

Конфигурация уменьшает очевидную поверхность: снаружи остаётся обычный TLS-сайт на TCP/443, REALITY использует локальный self-steal, панель и subscription backend не публикуются напрямую, Nginx не пишет access log и не раскрывает версию в заголовках. SNI в REALITY — тот же домен, который обслуживает локальный Nginx; обычный или не прошедший REALITY ClientHello попадает на собственный cover-site. Чужой и отсутствующий SNI также не должны раскрывать панель. Не меняйте REALITY target на случайный внешний сайт: при неуспешной авторизации сервер может превратиться в нежелательный forwarder, а сетевой профиль станет зависеть от чужой инфраструктуры.

`ssl_reject_handshake` намеренно не включён: обычная выдача cover-site с несовпадающим сертификатом для чужого SNI совместимее между поддерживаемыми версиями Nginx и похожа на типичный однодоменный сервер. HTTP/2 включается синтаксисом, соответствующим установленной версии Nginx (`listen ... http2` до 1.25.1, директива `http2 on` в новых версиях).

Абсолютной «невидимости VPN» нет. Наблюдатель всё ещё видит IP и ASN дата-центра, время и объём соединений; провайдер VPS видит процессы и метаданные сервера. Для устойчивого профиля важнее:

- отдельный домен без Cloudflare proxy (DNS only), корректный TLS и правдоподобный, быстрый cover-site;
- только необходимые входящие порты; панель — localhost/Tailscale либо строгий allowlist;
- SSH-ключи вместо пароля; после проверки отдельного sudo-пользователя можно запретить password login и прямой root login, не меняя SSH одновременно с первой установкой VPN;
- актуальный Xray/3x-ui после тестирования обновления, регулярная проверка CVE и резервная копия перед обновлением;
- уникальные UUID/subId для каждого пользователя, немедленная блокировка потерянного устройства и отсутствие общих подписок;
- отсутствие секретов в публичных логах, issue и скриншотах; state/result-файлы остаются `0600` и доступны только root;
- мониторинг необычного трафика, диска, памяти и входов SSH без записи полных subscription URL.

Не включайте случайные `fragment`, `finalmask`, нестандартные TLS-заголовки и постоянно меняющиеся padding-настройки только ради «маскировки»: они могут добавить устойчивый отпечаток, ухудшить совместимость или открыть уязвимость. XHTTP-параметры меняйте только по документации текущей версии и с внешним тестом из нужных сетей.

## Профиль памяти 3x-ui / XHTTP

Новая установка и восстановление применяют общие `bufferSize`/`connIdle` для обоих транспортов. Настройки XMUX применяются только к XHTTP:

| Параметр | Значение | Где действует |
|---|---|---|
| `policy.levels.0.bufferSize` | `64` КиБ | Буфер внутренних pipe Xray уровня 0 |
| `policy.levels.0.connIdle` | `180` секунд | Простой проксируемой сессии уровня 0 |
| `xmux.maxConcurrency` | `"0"` | Только XHTTP: отключает выбор пула по concurrency |
| `xmux.maxConnections` | `"1"` | Размер клиентского пула XMUX |
| `xmux.cMaxReuseTimes` | `"0"` | Без ограничения по этому счётчику |
| `xmux.hMaxRequestTimes` | `"300-600"` | Порог запросов для смены транспорта |
| `xmux.hMaxReusableSecs` | `"600-900"` | Окно повторного использования транспорта |
| `xmux.hKeepAlivePeriod` | `0` | Значение по умолчанию ядра |

Это снижение нагрузки на память, а не исправление доказанной утечки в Xray. `bufferSize` не выделяется целиком каждому TCP-сокету и не ограничивает всю память процесса; линейную экономию по числу ESTAB обещать нельзя. `connIdle` не закрывает простаивающий внешний HTTP/2 transport. `hMaxReusableSecs` проверяется при выборе транспорта; активные запросы могут пережить этот срок. `maxConnections=1` не является жёстким пределом общего числа сокетов при ротации.

XMUX хранится в inbound панели для передачи клиентам через подписку. Обновите подписки и переподключите клиентов; на ноде проверьте также профиль, выдаваемый главной панелью. Строковые значения сохраняют совместимость экспорта в Mihomo. Старые клиенты могут игнорировать эти поля. Остальные уровни policy не меняются.

Для уже работающего сервера, установленного этим проектом, скопируйте `optimize-xhttp-memory.sh` рядом с установленными скриптами и выполните:

```bash
sudo bash /root/optimize-xhttp-memory.sh
```

Скрипт читает локальный state-файл и обновляет policy уровня 0. Для XHTTP он также обновляет XMUX inbound `in-443-xhttp-reality`; для Vision сохраняет transport без изменений. Клиенты, ключи, пути, лимиты и маршрутизация не сбрасываются. Перед записью создаётся закрытая папка `/root/xhttp-memory-backup.*` с online-копией SQLite и исходными JSON. При уже применённом профиле повторный запуск ничего не меняет. При изменении выполняется перезапуск Xray, текущие соединения могут оборваться. Не запускайте параллельно с редактированием панели.

Если сохранение частично завершилось, путь к резервной копии выводится в ошибке. Исходный `xray.json` можно вернуть через редактор Xray Configs, а `inbound.json` — через API update того же inbound. Восстановление полной БД делайте только при остановленном `x-ui`, сохранив текущее состояние и учитывая файлы WAL/SHM; это откат всех изменений панели после копии.

Сравните RSS, swap, FD, ESTAB и goroutine при сходной нагрузке до изменения, через 30 минут и через сутки. Снижение сразу после рестарта само по себе не доказывает устранение утечки. При тысячах внешних H2-соединений потребуется также обновление/исправление ядра или клиентского транспорта; регулярные рестарты и `MemoryMax` не заменяют диагностику.
